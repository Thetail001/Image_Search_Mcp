# 配置变更说明（随安全修复交付）

本批修复改动了**运行期行为**，不是纯内部重构。运维和调用方需要按下面调整，
否则会出现"服务起不来"或"原本能用的调用现在报错"。

每条都标了：变更前 → 变更后 → 需要做什么 → 不做什么会怎样。

---

## 一、部署侧

### 1. HTTP 模式缺 token 时拒绝启动

- **变更前**：`MCP_AUTH_TOKEN` 为空也照常启动，服务对任何能连上的人开放
- **变更后**：报错并以非零码退出
- **需要做什么**：确认部署环境里有 `MCP_AUTH_TOKEN`（非空白）。现有的值是 64 位随机串，不用换
- **不做会怎样**：进程起不来。这是刻意的 —— 旧行为是"静默匿名"，比起不来危险得多
- **仅本机调试**：`IMAGE_SEARCH_ALLOW_ANONYMOUS=1` **且** `--host 127.0.0.1`。
  对 `0.0.0.0` 开匿名会被拒绝启动

### 2. 免认证路径收窄成 `/healthz`，且只对 GET/HEAD

- **变更前**：`/` 无条件放行（任意方法）；健康检查打 `/` 也能通
- **变更后**：只有 `/healthz` 的 GET/HEAD 免认证；`/` 需要 Bearer token
- **需要做什么**：把监控/探针的目标从 `/` 改成 `/healthz`
- **不做会怎样**：探针收到 401，被判定为不健康，可能触发重启循环
- **`/healthz` 的语义**：只回答"进程活着、应用装起来了"。**刻意不访问任何引擎** ——
  真实搜图会烧配额，还会让上游抽风传导成本机重启

### 3. 带 `Origin` 头的请求默认被拒

- **变更前**：不看 `Origin`
- **变更后**：带 `Origin` 的请求必须出现在 `IMAGE_SEARCH_ALLOWED_ORIGINS`（逗号分隔）里，
  否则 403。**不带 `Origin` 的请求不受影响**（原生 MCP 客户端不发这个头）
- **需要做什么**：如果客户端是浏览器页面，把它的来源写进 `IMAGE_SEARCH_ALLOWED_ORIGINS`。
  服务端到服务端的客户端通常什么都不用做
- **不做会怎样**：浏览器类客户端拿到 403
- **启动时会打印提示**：没配这个变量时会明确说明"带 Origin 的请求会被拒"

### 4. WebSocket 一律拒绝

- **变更前**：WebSocket 连接会掉进只认 `scope["method"]` 的处理器，报 `KeyError: 'method'`
- **变更后**：握手阶段明确以 1008（policy violation）关闭
- **需要做什么**：无。这个服务不需要 WebSocket 通道
- **说明**：旧行为是 bug 不是功能 —— 它没给出可用的工具调用，只是报错方式很难看

### 5. 协议端点路径显式钉住

- **变更前**：`mcp.http_app(transport="sse")` 吃上游默认值
- **变更后**：显式 `path="/sse"`，消息端点仍是 `/messages`
- **需要做什么**：无，路径没变
- **说明**：实测过 `path` 参数对 `transport="sse"` 控制的是 **SSE 端点本身**
  （传 `/messages` 会让两个路由撞在一起），而 `path="/"` 也合法 —— 那正是
  "协议端点挂到根路径上"的成因。钉住它比信任默认值可靠

## 二、引擎凭据

### 6. `IMAGE_SEARCH_COOKIES`（全局）不再被接受

- **变更前**：一个全局 cookie 串被应用到所有引擎
- **变更后**：检测到全局变量就**拒绝这次调用**，并指出该用哪个变量名
- **需要做什么**：改成按引擎命名 —— `IMAGE_SEARCH_COOKIES_YANDEX`、
  `IMAGE_SEARCH_COOKIES_EHENTAI`、`IMAGE_SEARCH_COOKIES_GOOGLE` ……
- **为什么必须改**：全局 cookie 不带域名，会跟着请求发给**任何**域名。
  实测把 `sid=ENGINE_COOKIE` 发到了 `untrusted.invalid` 和 `api.trace.moe`。
  按引擎归属之后才能限定"只发给这个引擎真正访问的域"
- **为什么不是"猜一个引擎发出去"**：猜错就是把 A 站凭据发给 B 站。宁可拒绝

### 7. 每个引擎的凭据只发给它自己的域

- **变更后**：Yandex 的 cookie 只去 `yandex.com`；EHentai 的只去 `e-hentai.org` / `exhentai.org`；
  以此类推。域名表对着上游源码核验过（有测试盯着，**双向**核验：
  表里的域必须在源码里出现，源码里的域也必须进表或写明豁免理由）
- **需要做什么**：无
- **线上现状**：这两个变量当前都是空的，属于**潜伏**缺陷 —— 谁哪天配上一个非空 cookie，
  旧代码就会以 `AttributeError: 'dict' object has no attribute 'split'` 炸掉
- **补充（随 A 报告补齐）**：凭据现在**只在 HTTPS 上发送**。
  `httpx.Cookies.set()` 造出的 cookie 是 `secure=False`，也就是说
  `http://<引擎域>/` 这个明文地址也会带上 cookie（已实测）。现在改为显式的仅 HTTPS
  - **需要做什么**：无。如果某个引擎走 `http://` 拿不到凭据，那是本项的预期结果

### 8. `IMAGE_SEARCH_PROXY`

- **值形态没变**：一个代理 URL 字符串，例如 `http://127.0.0.1:7890`
- **改的是内部处理**：旧代码把解析结果当字典传给上游（要字符串），非空必炸
  （`AttributeError: 'dict' object has no attribute 'url'`）。现在传字符串
- **需要做什么**：无
- **补充（随 A 报告补齐）**：环境里的 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`
  现在**真的**不生效了。此前"不读环境代理"只是一句声明：httpx 默认 `trust_env=True`，
  而它是在**构造时**就把环境代理编译成挂载点存下来的（`AsyncClient.__init__`），
  拿到的 client 上再改 `trust_env` 无效 —— 带凭据的引擎请求会悄悄走那个代理。
  现在会在拿到 client 后把继承来的代理挂载拆掉，并在日志里 `WARNING` 报出被拆的 pattern
  - **需要做什么**：如果这台机器**只有**通过环境变量配的代理才能出网，那么引擎请求
    现在会直连并失败。这种部署必须改配显式的 `IMAGE_SEARCH_PROXY`
  - **不做会怎样**：能连上但走代理的部署不受影响；只能靠环境代理出网的部署会看到
    引擎请求连接失败，日志里同时有"已拆掉从环境继承的代理挂载"这一条

### 9. 取图走本机的那两个引擎改了下载路径

- **涉及**：EHentai、BaiDu —— 它们的 `search()` 内部会用**本机**去下载 URL
- **变更后**：由本项目自己的下载器取图（地址校验、逐跳重定向校验、体积与总期限预算），
  再把字节交给引擎。引擎不再发起那次下载
- **需要做什么**：无。若目标图床在内网或非公网地址，会被拒绝 —— 这是预期行为
- **说明**：安全下载器的契约已按 A 报告的复核结论收口（总期限覆盖 DNS、读前拒绝压缩响应、
  显式特殊网段表、URL 规范化与原因归类），不再是"先接管入口"

## 三、调用侧（会打破既有调用）

### 10. `extra_params` 不再接受未知或保留的键

- **变更前**：`search_kwargs.update(extra_params)` —— 任何键都会被塞进引擎调用
- **变更后**：只接受该引擎**真实支持**的参数；未知键报错并给出正确名称；
  保留键（`file` / `url` / `client` / `api_key` / `cookies` / `proxies` 等）一律拒绝
- **需要做什么**：检查现有调用。以下写法现在会报错：

  | 旧写法 | 现在 | 原因 |
  |---|---|---|
  | `{"cutBorders": false}` | `{"cut_borders": false}` | 上游真实参数名下划线 |
  | `{"rpt": "imageview"}` | 删除 | Yandex 的 `search()` 只接 `url`/`file`，这个参数不存在 |
  | `{"cbir_page": "similar"}` | 删除 | 同上 |
  | `{"output_type": "json"}` | 删除 | 不在任何引擎签名里 |

- **为什么这是必要的**：`{"file": "/etc/passwd"}` 曾经能覆盖输入，
  上游 `read_file()` 会把该路径读出来**上传到搜索引擎站点**。已用哨兵内容实测确认
- **也是修一个谎**：README 里写的 `cutBorders` 从来没生效过

### 11. `limit` 必须落在 1–50

- **变更前**：`limit=0` 会**真的发一次搜索请求**却返回 0 条；`limit=-1` 报 "top -1" 却给 2 条
- **变更后**：越界或非整数直接报错，且**在发出任何请求之前**拒绝
- **需要做什么**：检查调用方是否传了 0 当"用默认值"。默认是 5

### 12. Base64 输入更严格

- 空串、空白、非法 base64、不是 base64 的 data URI、超过 16 MiB 的图
  → 明确报错，且不发出任何请求
- **需要做什么**：无（正常图片不受影响）

### 13. 错误输出不再带堆栈

- **变更前**：返回值里拼了 `traceback.format_exc()`，含服务端绝对路径
- **变更后**：对外只有简短说明；完整堆栈进服务端日志
- **需要做什么**：如果排查流程原本依赖返回值里的堆栈，改看日志

### 14. 失败的调用现在带 `isError: true`

- **变更前**：输入不合法、引擎报错、取图失败……全部作为**正常结果**返回，内容是一条以
  `Error: ` 开头的文本。协议层面看不出这是一次失败
- **变更后**：这些情况一律以 `isError: true` 返回（MCP 规范里的"工具执行错误"），
  文本内容与措辞**不变**。`get_engine_info` 收到不存在的引擎名同理
- **需要做什么**：客户端如果靠"文本以 `Error: ` 开头"来判断失败，改成看 `isError`；
  不改也仍然能用（文本协议没动）
- **不会变的**：**"没搜到结果"不是错误** —— 那是一次成功的搜索，仍是 `isError: false`。
  把它标成错误会让模型去"修"一个并不存在的问题
- **顺带**：错误里不带 `Error calling tool 'x': ` 这类框架前缀（那是用 `ToolError`
  而不是让裸异常冒出去的理由；裸异常会被 fastmcp 加上前缀）

### 15. 搜索结果新增 `structuredContent`

- **变更前**：只有人读文本，调用方要拿数据只能解析文本
- **变更后**：同时返回 `structuredContent`，并按声明的 `outputSchema` 约束形状：
  `engine`、`result_count`、`returned`、`truncated`、`results[]`（每项含
  `title`/`url`/`thumbnail`/`similarity`）
- **需要做什么**：无（纯新增）。想要机器可读结果的调用方可以开始用 `structuredContent`
- **口径说明**：`similarity` 各引擎不一致，可能是数字也可能是 `"95%"` 这类字符串，
  所以 schema 里允许 `number | string | null`。引擎特有字段（`episode`、
  `author_url` 等）**只在文本里**，没进结构化输出 —— 宁可少给也不给形状不定的东西

### 16. 工具声明带上标题与注解

- **变更后**：`search_image` 声明 `readOnlyHint=true`、`idempotentHint=true`、
  `openWorldHint=true`；`get_engine_info` 前两个相同但 `openWorldHint=false`（纯本地）
- **需要做什么**：无。这是给客户端用的：之前这两个只读工具不声明注解，
  客户端只能一律当危险操作处理（每次弹确认，或者干脆不给用）

### 已知偏差（记在案，不是我们引入的）

- **未知工具**：规范把"未知工具"归为协议错误（JSON-RPC error，如 `-32602`），
  但 `fastmcp 4.0.10` 把它变成 `isError: true` 的工具执行错误（实测）。
  实用影响很小（消息可操作），所以不为了对齐规范去跟框架硬扛；
  这条偏差有测试盯着，框架改了会红

## 四、刻意**没有**改的（避免误以为"顺手都改好了"）

- **默认传输与路径**：仍是 SSE 模式 + `/sse` + `/messages`
- **`/healthz` 仍然存在且免认证**（只收窄到 GET/HEAD）
- **引擎列表不变**：还是 11 个。上游 `main` 分支里的 Google 已废弃、Bing 需要解密签名、
  还有三个 3.12.11 里没有的引擎 —— 本批**不引入**它们
- **`IMAGE_SEARCH_API_KEY` 仍然只从环境读**，不接受调用方传入
- **safe downloader 的完整契约**（代理下的 DNS 归属、预算数值、生命周期）仍在批次 2，
  本批只接管了入口

## 五、部署后自检

```bash
# 1. 服务是否起来了（缺 token 会直接退出，日志里有说明）
systemctl status image-search-mcp

# 2. 健康检查免认证可达
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/healthz   # 期望 200

# 3. 根路径现在需要 token
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/          # 期望 401

# 4. 带 token 能通
curl -sS -o /dev/null -w '%{http_code}\n' \
     -H "Authorization: Bearer $MCP_AUTH_TOKEN" http://127.0.0.1:8000/    # 期望 200

# 5. 没有 token 的工具调用必须被拒（这条对应修掉的那个认证绕过）
curl -sS -o /dev/null -w '%{http_code}\n' \
     -X POST http://127.0.0.1:8000/messages/                             # 期望 401
```

第 5 条是本批最要紧的验收：旧代码在这个请求上返回过 `200` 并把工具集泄了出去。
